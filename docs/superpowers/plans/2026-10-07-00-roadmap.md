# Craftoria v2 — Master Roadmap

Start here. This file sequences the 15 implementation plans (106 tasks) that take Craftoria from the legacy Express + MongoDB app to a production-ready, multi-vendor microservices marketplace on PostgreSQL.

- **The spec** (what and why): `docs/architecture/01…05`. Every agent reads `05-engineering-standards.md` before every task.
- **The plans** (how, task by task): `docs/superpowers/plans/2026-10-07-01…15`.
- This file covers order, parallelism, milestones, agent dispatch and risks.

## 2. Dependency graph and phases

```
Phase 0 ── 01 legacy hotfix (if live)            Phase 0 runs in parallel with everything
              │
Phase 1 ── 02 foundation  T1→T2→T3→T4 ─┬─→ T5→T6→T7→T8→T9→T10 ─→ T11 → T12
                                        │  (contracts done: frontends may start)
                                        ▼
Phase 2 ── services in parallel ── 03 identity │ 04 catalog │ 05 seller │ 06 cart │ 07 order │ 08 payment │ 09 notification │ 10 gateway
           frontends in parallel ── 11 storefront (MSW mocks) → 12 console
           infra in parallel ────── 14 T1–T5 (owner: Oracle + Cloudflare accounts)
                                        │
Phase 3 ── integration ─── 15 T1–T2 (E2E on compose) · 13 migrator · 14 T6–T8 (staging live)
                                        │
Phase 4 ── hardening ───── 15 T3 load/race · 15 T4 security · 15 T5 go-live checklist
                                        │
Phase 5 ── cutover ─────── 15 T6 rehearsal → go/no-go → DNS switch → T+30d decommission
```

Why this order:
- **Contracts first** (plan 02 Tasks 3–4) is what lets eight services and two frontends be built in parallel by different agents. Every DTO, internal API and event payload is fixed before any service code exists. Changing a contract later is allowed, but it is a serial, reviewed change (see §5).
- Within each service plan, tasks are **sequential** (each builds on the previous one's repository and module layout).
- Order (07) does not wait for catalog, cart or payment, because it talks to them through ports with fakes. Real integration is proven in plan 15.

Rough calendar for **one owner reviewing plus 3–4 agents in parallel**: M1 ≈ 1.5–2 weeks, M2 ≈ +3–4 weeks, M3 ≈ +2–3 weeks (overlaps M2), M4 ≈ +1–2 weeks (owner time on accounts), M5 ≈ +1–2 weeks. That is about **10–13 weeks** in total. The real bottleneck is your review bandwidth, not agent speed.

## 4. How to dispatch agents

**Concurrency.** Run at most **3–4 implementer agents at once**, each in its own git worktree (`using-git-worktrees`), each on a different lane. More than that and you can't review properly, and review is the quality gate.

**Suggested lane schedule after M1:**

| Wave | Agent 1 | Agent 2 | Agent 3 | Agent 4 |
|---|---|---|---|---|
| 1 | 03 identity | 04 catalog | 07 order | 11 storefront T1–T3 |
| 2 | 08 payment | 05 seller | 12 console T1–T3 | 11 storefront T4–T7 |
| 3 | 09 notification | 10 gateway | 12 console T4–T6 | 11 storefront T8–T10 |

**Plan 06 (cart) is built by the owner in parallel at their own pace**, any time after plan 02 Task 10 (service generator) and Task 11 (local infra) exist. Plan 15 (E2E) is the first point that needs the finished cart.
| 4 | 13 migrator | 15 T1–T2 (E2E) | 14 (agent parts) | — |

**One task = one agent run.** Extract the task brief with the repo script so the implementer sees exactly one task:

```bash
.claude/skills/subagent-driven-development/scripts/task-brief docs/superpowers/plans/2026-10-07-04-catalog-service.md 9
```

**Implementer prompt template** (paste with the brief):

```text
You are implementing ONE task of the Craftoria v2 rebuild.
Read first, in order:
  1. docs/architecture/05-engineering-standards.md (mandatory rules, Definition of Done)
  2. The spec sections listed in the plan header: <paste "Spec:" line>
  3. The plan header's "Global Constraints" and "Review Focus" for this plan
  4. The task brief: <path to task-N-brief.md>
Skills: load every skill named on the task's "Skills:" line (from .claude/skills/, or .agents/skills/ in
Antigravity) before writing code. Use ONLY this project's skill pack — no global skills, no plugins, no
other design/backend skills. Backend tasks start with safe-backend-changes; buyer-facing UI tasks start with
handcrafted-storefront-ui and end with web-design-guidelines. If a skill you need is missing, say so in the report.
Work on branch feat/<plan>-<task>-<slug> in your worktree. Follow TDD: write the listed failing tests first,
run them and show the failure, implement, run and show them passing, then lint + typecheck.
Do not change packages/contracts or another service's code; if you believe a contract is wrong, stop and
report the exact change you need. Do not edit merged migrations. Commit with the message given in the task.
Finish with a report: files changed, test output (pasted), any deviations from the plan and why.
```

**Reviewer gate** (`requesting-code-review`): check that the task's listed skills were followed (for UI tasks the `web-design-guidelines` findings are resolved; for backend tasks the `safe-backend-changes` rules hold), then check against the task's Interfaces block, the plan's Global Constraints, doc 03 contracts (exact paths, shapes and error codes), and doc 05 Definition of Done. Reject on any deviation that is not justified in the report.

**Merge order.** Merge each service's tasks in order into `main` (via PR). Conflict hotspots are `infra/compose/*.yml`, `infra/env/.env.example` and `pnpm-lock.yaml`: rebase before merging and regenerate the lockfile rather than hand-merging it.

## 5. Change control for contracts

`packages/contracts` and `docs/architecture/03-…` are the shared language of all agents. A change to them:
1. is proposed by the agent that hit the problem, as a short note: what, why, which consumers are affected;
2. is approved by you;
3. is implemented in a **dedicated PR** (contracts + doc 03 + fixtures) before the dependent work continues;
4. must be backward compatible (new optional fields, or a new `vN+1` event) unless no consumer is merged yet.

## 6. Risk register

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Legacy C1 exploit used before the rewrite ships | Medium | High (free orders) | Plan 01 first, if the legacy site is live |
| Oracle A1 capacity unavailable or account reclaimed | Medium | High | Free Tier only (D-8): accept that idle VMs may be stopped; less busy home region, off-provider backups to R2, DR runbook (2 h RTO) |
| Distributed-system bugs (lost events, double processing) | Medium | High | Outbox/inbox in service-kit with race tests; DLQ alerts; E2E timeout and late-payment journeys |
| Oversell of one-of-a-kind items | Low (designed out) | High | Conditional-update reservations, concurrency tests (catalog T9) and the k6 race (plan 15 T3) |
| Agents drifting from contracts | Medium | Medium | Contracts-first, doc 03 as reference, a reviewer gate on Interfaces, contract tests with shared fixtures |
| Owner review bandwidth | High | Medium | Cap 3–4 parallel agents; small tasks; strict Definition of Done reduces review effort |
| Single-VM downtime during deploys (a few seconds per container) | High | Low | Deploy off-peak; zero-downtime rollouts are a post-launch improvement |
| Free-tier limits (Resend 100 emails/day, R2 10 GB, Grafana series) | Medium (at growth) | Low | Metrics on usage; each provider sits behind a port, so swapping is a config change |
| Tax and compliance obligations (GST TCS, DPDP, e-commerce rules) | Medium | High | CA review before launch (plan 15 T5); data model already stores GSTIN, HSN and tax rates |
