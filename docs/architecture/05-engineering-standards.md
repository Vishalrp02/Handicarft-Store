## 2. Service template (every service looks like this)

```
services/<name>/
├── src/
│   ├── main.ts                bootstrap: loadConfig → createDb → connect broker → buildApp → listen → start workers → graceful shutdown
│   ├── app.ts                 buildApp(deps: AppDeps): express.Express   ← used by supertest; no I/O at import time
│   ├── config.ts              export const ConfigSchema = z.object({...}); export type Config
│   ├── deps.ts                export interface AppDeps { config, db, logger, publisher, clock, ...ports }
│   ├── db/
│   │   ├── schema.ts          Kysely `DB` interface (generated by kysely-codegen, committed)
│   │   └── migrations/        0001_init.ts, 0002_….ts  (export async function up(db) / down(db))
│   ├── modules/<feature>/
│   │   ├── <feature>.routes.ts       router wiring only: validate(), requireAuth(), controller fn
│   │   ├── <feature>.controller.ts   parse input (zod from contracts) → call service → shape DTO
│   │   ├── <feature>.service.ts      business logic; takes deps + plain args; NO req/res, NO SQL
│   │   ├── <feature>.repository.ts   Kysely queries only; accepts `Executor` (db or trx)
│   │   ├── <feature>.mapper.ts       row → DTO functions
│   │   └── <feature>.test.ts         unit tests for service/pure logic (fakes for repos)
│   ├── events/
│   │   ├── handlers/<event-type>.handler.ts   one file per consumed event
│   │   └── consumers.ts       registers handlers with createConsumer()
│   └── jobs/<job>.job.ts      periodic jobs (setInterval wrapped by service-kit runJob with a pg advisory lock)
├── test/integration/*.int.test.ts   supertest + Testcontainers Postgres (+ RabbitMQ where needed)
├── Dockerfile                 multi-stage, node:24-bookworm-slim, non-root `node` user, `pnpm deploy --prod`
├── package.json               scripts: dev, build, start, test, test:int, lint, typecheck, migrate, migrate:down, db:types
└── tsconfig.json
```

Layer rules (from `safe-backend-changes`): routes → controller → service → repository. No SQL outside repositories. No `req`/`res` outside routes/controllers. Services receive a `Clock` (`{ now(): Date }`) instead of calling `new Date()`, so time-based logic is testable.

## 3. Coding conventions

- TypeScript `strict: true`, `noUncheckedIndexedAccess: true`, `exactOptionalPropertyTypes: false`. ESM (`"type": "module"`), with Node `--enable-source-maps`.
- No `any` (lint error); use `unknown` and narrow it. No non-null `!` except in tests.
- Naming: files `kebab-case.ts` with a role suffix (`order.service.ts`); types `PascalCase`; functions `camelCase`; DB columns `snake_case`, mapped to camelCase in mappers (Kysely `CamelCasePlugin` is **not** used, so the mapping stays explicit).
- Errors: throw `AppError` subclasses from `@craftoria/service-kit/errors` (`NotFoundError`, `ConflictError(code, details)`, `BusinessRuleError(code, details)`, …). Never `res.status(500).json(err.message)`.
- Money: only `@craftoria/contracts/money` helpers (`assertPaise`, `sumPaise`, `multiplyPaise`, `percentOfPaise(amount, bps)`). Never `* 100` on user input; never floats for money.
- Logging: `deps.logger.info({ orderId }, 'order paid')`. Structured fields first, message second. Never log tokens, passwords, full addresses, bank numbers or Razorpay signatures.
- Config: everything via `config.ts`; `process.env` is read **only** in `config.ts`.
- Dates: stored `timestamptz`, serialised `toISOString()`.
- **Styling (frontends): Tailwind CSS v4 only.** Design tokens live once in `@craftoria/ui` as a Tailwind `@theme` (`packages/ui/src/theme.css`) and both apps import it; use token-backed utilities (`bg-surface`, `text-kohl`, `font-heading`), never raw hex values or arbitrary values like `bg-[#123456]`. No CSS-in-JS, no CSS modules, no component kits (MUI, Chakra, Ant, Bootstrap). Plain CSS is allowed only in `theme.css` and for print styles. Class order is enforced by `prettier-plugin-tailwindcss`; conditional classes use `clsx` + `tailwind-merge` via `cn()` from `@craftoria/ui`.
- Dependencies: adding a runtime dependency to a service needs a one-line justification in the PR description. No new major framework without updating the architecture docs.

## 4. Testing

| Level | Tool | Where | What |
|---|---|---|---|
| Unit | Vitest | `src/**/*.test.ts` | pure logic: state machines, money, pricing, mappers, services with fake repos |
| Integration | Vitest + supertest + Testcontainers (`postgres:17-alpine`, `rabbitmq:4-management-alpine`) | `test/integration/*.int.test.ts` | real HTTP → real SQL; event publish (outbox row) and consume (handler with inbox) |
| Contract | Vitest | producer: integration test parses the outbox payload with the contracts schema; consumer: handler test loads `@craftoria/contracts/fixtures/<type>.v1.json` | events stay compatible |
| E2E | Playwright | `/e2e` | full compose stack with `PAYMENT_PROVIDER=fake` |
| Load | k6 | `/e2e/load` | checkout path and the one-of-a-kind stock race |

Rules:
- TDD: write the failing test first (`test-driven-development` skill).
- Each integration test file gets a fresh database: `createTestDb()` from `@craftoria/service-kit/testing` runs migrations on a unique database inside one shared container per test run.
- Never mock the database in integration tests. Mock external SaaS only (Razorpay, Resend, R2) through the service's port interfaces (`PaymentGateway`, `EmailProvider`, `ObjectStorage`).
- Coverage floor per service: 80 % lines on `src/modules/**` and `src/events/**`, enforced in CI.
- Test helper for auth: `makeTestToken({ sub, roles, sellerId? })` signs with a test Ed25519 key, and `testJwks()` returns the matching JWKS the service is configured with in tests.

## 5. Migrations

- Kysely `Migrator` with `FileMigrationProvider`; file names `NNNN_snake_description.ts`, 4-digit zero-padded.
- Every migration has `up` **and** a working `down`. CI runs `up → down → up` on a fresh database for every service.
- Never edit a migration that has been merged to `main`. Expand → migrate → contract for destructive changes (see `safe-backend-changes`).
- Production migrations run only via the deploy pipeline (`docker compose run --rm <svc> node dist/migrate.js latest`), never from a laptop or an AI session.
- After changing schema: `pnpm --filter @craftoria/<svc> db:types` regenerates `src/db/schema.ts`; commit it.

## 6. Git and review workflow

- Branch per plan task: `feat/<plan-no>-<task-no>-<slug>`, e.g. `feat/07-03-checkout-endpoint`. Never commit to `main`.
- Conventional Commits: `feat(order): …`, `fix(catalog): …`, `test(…)`, `chore(…)`, `docs(…)`.
- PR template sections: What / Why / How tested (paste the command output) / Contracts changed? / Migrations? / Rollback.
- CI must be green: lint, typecheck, unit, integration, migration round-trip, build. Docker images build only on `main`.
- Contract changes (`packages/contracts`) need the docs in `docs/architecture/03-…` updated **in the same PR**.

## 7. Definition of Done (per task)

A task is done only when all of these hold:
1. Tests written first, now passing: `pnpm --filter <pkg> test` and `test:int`, with the output pasted in the task report.
2. `pnpm -w lint && pnpm -w typecheck` are clean.
3. No TODOs without a linked plan task; no `console.log`.
4. New env vars are added to `config.ts`, `infra/env/.env.example`, and `infra/compose` files.
5. New endpoints appear in the service's OpenAPI (`/openapi.json`) and match `03-api-and-event-contracts.md` exactly.
6. New events: schema and fixture in contracts; the producer test validates the payload.
7. Committed on the task branch with a Conventional Commit message.

## 8. Skills: mandatory and exclusive

This project ships its own skill pack in `.claude/skills/` (Claude Code) and an identical copy in `.agents/skills/` (Antigravity, Cursor, Codex). **Agents must use only these 26 skills for Craftoria work.** Do not use any other skill, plugin or global skill (for example from `~/.claude/skills`, a marketplace plugin, or another design or backend skill pack), even if one seems relevant. If a needed capability is missing from the list, say so in the task report instead of reaching for an outside skill.

Every plan task has a `**Skills:**` line naming the skills for that task. Load those skills before writing code, plus the workflow skills that apply to every task.
